## Задание 1. Исследование моделей и инфраструктуры

### Контекст и ограничения

База знаний: ~21 250 документов (Markdown, Confluence, PDF‑спецификации), рост ~400 страниц/мес. Документация содержит клиентский IP под NDA (ABB, Wärtsilä), компания проходит ежегодный SOC 2‑аудит. Часть документов — на финском и эстонском.  
Стек реализации: Python 3.11, LangChain, Docker Compose, AWS EKS.

**Ключевое ограничение:** передача NDA‑материалов внешним провайдерам недопустима. Это определяет выбор в пользу локальных решений.

---

### 1. Сравнение LLM‑моделей (локальные vs облачные)

| Критерий | Локальные (Qwen3‑30B‑A3B) | OpenAI (GPT‑4o / mini) | YandexGPT |
| --- | --- | --- | --- |
| **Качество** | 80,9 % MMLU‑Pro — достаточно для RAG | GPT‑4o — лидер рынка; mini — сопоставим с локальными 20–30B | Приемлемое, уступает GPT‑4o |
| **Скорость** | 40–80 ток/сек, без сетевой задержки | 80–120 ток/сек + 50–200 мс сеть | 50–70 ток/сек + сеть |
| **Стоимость** | Аренда сервера ~\$400–1200/мес, без платы за токены | mini — ~\$18/мес при 1000 запросов/день | ~\$20–77/мес |
| **Развёртывание** | Ollama — одна команда | API‑ключ, тривиально | API‑ключ |
| **Конфиденциальность** | Данные внутри периметра | **Нарушение NDA** | **Нарушение NDA, юрисдикционные риски** |

**Вывод:** YandexGPT исключён (риски GDPR и SOC 2 для EU‑компании). OpenAI дешевле и качественнее, но передача NDA‑материалов недопустима.  
**Выбор: Qwen3‑30B‑A3B через Ollama.** MoE‑архитектура (3,3 B активных параметров) даёт качество уровня 70B при VRAM‑затратах 7B. Для RAG (поиск по контексту, формирование ответа) этого достаточно. Ollama обеспечивает простоту запуска; OpenAI‑совместимый API позволяет при необходимости мигрировать на vLLM без изменения кода.

---

### 2. Сравнение моделей эмбеддингов (локальные vs облачные)

| Критерий | BAAI/bge‑m3 (локально) | OpenAI text‑embedding‑3‑small |
| --- | --- | --- |
| **Качество (MTEB)** | ~63 | 62,3 |
| **Скорость индексации** | ~15 мин на GPU для 106 K чанков | Высокая при параллельных вызовах + сетевая задержка |
| **Стоимость** | Бесплатно | ~\$1 за весь корпус |
| **Многоязычность** | 100+ языков, включая FI/EE | Ограниченная |
| **Конфиденциальность** | Данные внутри | Массовая передача корпуса наружу |

**Вывод:** стоимость OpenAI Embeddings пренебрежимо мала, но индексация требует передачи всего корпуса — то же нарушение NDA.  
**Выбор: BAAI/bge‑m3.** Качество сопоставимо с OpenAI (63 vs 62,3 MTEB). Поддержка финского и эстонского — прямая потребность QuantumForge. Размерность 1024 — баланс между компактностью индекса (~435 МБ) и качеством. Dense + sparse retrieval в одной модели — возможность улучшить поиск без замены.

### 3. Сравнение векторных баз (ChromaDB vs FAISS)

| Критерий | ChromaDB | FAISS |
| --- | --- | --- |
| **Скорость поиска** | 2,58 мс/запрос | 0,34 мс/запрос |
| **Метаданные** | Встроенные, фильтрация из коробки | Отсутствуют — нужна внешняя SQL‑база + синхронизация |
| **Персистентность** | Встроенная | Ручная реализация |
| **API** | Python SDK, HTTP‑сервер, Docker | Библиотека, нет API‑слоя |
| **Развёртывание** | `pip install chromadb`, embedded‑режим | Сборка, persistence‑слой, обёртка конкуренции |
| **Масштаб** | До ~10 M векторов | Миллиарды (доказано Meta) |
| **Стоимость** | Бесплатно (Apache 2.0) | Бесплатно (MIT) |

**Вывод:** разница в скорости (2 мс) незначительна при времени LLM‑генерации 2–5 секунд. Для QuantumForge нужна фильтрация по отделу, типу документа, дате — ChromaDB даёт это из коробки. В FAISS для этого требуется отдельная SQL‑база, код синхронизации и самописная логика фильтрации — недели разработки и дополнительные точки отказа. Объём QuantumForge (~106 K чанков) далёк от лимитов ChromaDB (~10 M).  
**Выбор: ChromaDB.** Метаданные, персистентность и API из коробки при достаточной скорости для текущего объёма.

---

### 4. Конфигурация сервера и варианты реализации

Расчёт: LLM (8‑bit) ~32–40 ГБ VRAM, ChromaDB ~4–8 ГБ RAM, bge‑m3 ~2 ГБ VRAM, ОС и сервисы ~12 ГБ RAM, запас 50 %.

| Параметр | Вариант 1: Пилот | Вариант 2: Production (рекомендуемый) | Вариант 3: Cloud API |
| --- | --- | --- | --- |
| **LLM** | Qwen3‑30B‑A3B (Ollama) | Qwen3‑30B‑A3B (Ollama / vLLM) | GPT‑4o‑mini (API) |
| **Эмбеддинги** | bge‑m3 (локально) | bge‑m3 (локально) | OpenAI text‑embedding‑3‑small |
| **Векторная БД** | ChromaDB (embedded) | ChromaDB (server mode) | ChromaDB (server mode) |
| **GPU** | 1× NVIDIA L4 (24 ГБ) | 1× NVIDIA L4 (24 ГБ) | Не требуется |
| **CPU** | 16 ядер | 16–32 ядра | 8 ядер |
| **RAM** | 64 ГБ | 128 ГБ | 32 ГБ |
| **Диски** | 1× NVMe 1 ТБ | 2× NVMe 1 ТБ | 1× NVMe 500 ГБ |
| **Стоимость/мес** | ~\$400–600 | ~\$700–1200 | ~\$50–100 |
| **Конфиденциальность** | Полная | Полная | **Нарушение NDA** |

- **Вариант 3 исключён:** передача NDA‑материалов в OpenAI нарушает клиентские соглашения.  
- **Вариант 1** достаточен для проверки концепции на 20–50 пользователей.  
- **Вариант 2 — рекомендуемый:** 128 ГБ RAM обеспечивают запас на 12–18 месяцев роста, 2× NVMe разделяют ОС и индексы. NVIDIA L4 — серверная карта (72 Вт, для стойки ЦОД); 24 ГБ VRAM достаточно для Qwen3‑30B‑A3B в 8‑bit.

---

### Итоговое решение

| Компонент | Выбор | Обоснование |
| --- | --- | --- |
| **LLM** | Qwen3‑30B‑A3B, Ollama | Качество 70B при VRAM 7B, данные внутри периметра, простота запуска |
| **Эмбеддинги** | BAAI/bge‑m3 | Многоязычность (FI/EE), качество ~OpenAI, без передачи данных |
| **Векторная БД** | **ChromaDB** | Метаданные и персистентность из коробки, скорость достаточна для 100–200 K чанков |
| **Сервер** | 1× L4, 32 ядра, 128 ГБ RAM, 2× NVMe | Покрывает все компоненты с запасом на 12–18 месяцев |

#### Обоснование выбора векторной БД (ChromaDB)

Для объёма QuantumForge (~106–130 K чанков) преимущество FAISS в скорости поиска (0,34 мс vs 2,58 мс) статистически незначимо на фоне LLM‑генерации (2–5 сек). Отсутствие в FAISS встроенных метаданных, персистентности и API‑слоя требует недель разработки и создаёт дополнительные точки отказа. ChromaDB закрывает эти потребности из коробки, а её лимитов (~10 M векторов) хватит на годы роста базы. Облачные LLM и эмбеддинги отклонены: передача NDA‑материалов нарушает клиентские соглашения и усложняет SOC 2‑аудит.

## Задание 3. Создание векторного индекса базы знаний

### Создание индекса

```bash
cd Task3
docker compose up -d
python build_index.py
```

### Проверка индекса

```bash
curl http://localhost:8000/api/v2/tenants/default_tenant/databases/default_database/collections
python check_index.py
```

После запуска `check_index.py` скрипт:

- выводит результаты в консоль (кратко, для быстрой оценки);
- формирует подробный отчёт в файле **`index_results.txt`** в той же папке.

В `index_results.txt` содержатся:

- дата и параметры проверки;
- все тестовые запросы;
- найденные фрагменты с указанием источника, ID чанка, дистанции (cosine similarity) и фрагмента текста.

Файл перезаписывается при каждом запуске и может использоваться как лог проверки или для анализа качества чанкинга.

## Задание 4. Реализация RAG-бота с техниками промптинга

RAG-бот с техниками Few-shot и Chain-of-Thought. Ищет факты в векторной базе ChromaDB, формирует промпт и отправляет в LLM.

### Структура папки

```text
Task4/
├── rag_bot.py        — модуль RAG + REPL-бот
├── demo.py           — демо-диалоги (5 успешных + 2 «Я не знаю»)
├── dialogues.txt     — отчёт демо (генерируется автоматически)
├── requirements.txt  — зависимости
```

### Подготовка к запуску

#### 1. ChromaDB и индекс (из Task3)

```bash
cd Task3
docker compose down -v
sudo rm -rf ./chroma_data
docker compose up -d
python build_index.py
```

#### 2. LLM-модель (Ollama)

```bash
ollama pull qwen2.5:7b
```

Сервис Ollama запускается автоматически после установки. Не нужно выполнять `ollama serve` вручную.

#### 3. Python-зависимости

```bash
cd Task4
pip install -r requirements.txt
```

### Запуск

#### Интерактивный режим (REPL)

```bash
python rag_bot.py
```

Вводите вопросы — бот ответит с шагами рассуждения и источниками. Введите `exit` для выхода.

#### Скрипт проверки (демо-диалоги)

```bash
python demo.py
```

Скрипт выполнит 7 запросов и сохранит результаты в `dialogues.txt`:

- **5 успешных диалогов** — ответы на основе базы знаний (оружие Ксарна Велгора, уязвимости Войд Кора, роль Громмака, технология HyperRelay, столица Ти'лора).
- **2 диалога «Я не знаю»** — вопросы вне базы (погода в Москве, арифметика), на которые бот обязан отказаться отвечать.

### Техники промптинга

#### Few-shot

В `rag_bot.py` в переменной `FEW_SHOT_EXAMPLES` заданы 2 примера из вселенной Aeon Nexus:

- Q: Как называется столица планеты Ти'лора? — A: Сайрон.
- Q: Какая технология питает HyperRelay? — A: VoidCore.

Модель видит формат ответа (шаги рассуждения → итоговый ответ) и повторяет его.

Если в вашей базе знаний нет этих фактов — замените `FEW_SHOT_EXAMPLES` в `rag_bot.py` на реальные данные из ваших файлов. Сохраняйте структуру: «Шаги рассуждения» → «Ответ».

#### Chain-of-Thought (CoT)

System-промпт содержит инструкцию:

> «Сначала размышляй шаг за шагом: пиши, что именно ты ищешь и где находишь это во фрагментах. После рассуждений дай чёткий итоговый ответ в строке „Ответ: …“».

Если информации нет в фрагментах, бот обязан ответить: «Я не знаю.»

### Конфигурация

| Параметр | Переменная окружения | По умолчанию |
| --- | --- | --- |
| API-ключ LLM | `LLM_API_KEY` | `ollama` |
| URL API LLM | `LLM_BASE_URL` | `http://localhost:11434/v1` |
| Модель LLM | `LLM_MODEL` | `qwen2.5:7b` |
| Кол-во чанков | `TOP_K` (в коде) | `4` |
| Эмбеддинги | — | `BAAI/bge-m3` |

#### Примеры переопределения

**Linux/macOS:**

```bash
export LLM_BASE_URL="http://localhost:11435/v1"
export LLM_MODEL="llama3.1:8b"
python demo.py
```

## Задание 5. Запуск и демонстрация работы бота

Проверяем, что бот не выдаёт секреты при промпт-инъекциях и отказывает, когда ответа нет в базе. Перед запуском скриптов нужно выполнить Задание 3. [Вредоносный файл](./Task2/knowledge_base/malicious.md) находится в базе начиная с Задания 2.

### Запуск скрипта проверки

Установите зависимости и запустите тесты:

```bash
cd Task5
pip install -r requirements.txt
python run_tests.py
```

Результат сохраняется в файле `test_results.txt`.

### Тесты

**Блок A (5 запросов по базе)** — ожидаем осмысленный ответ из фрагментов базы.

**Блок B (5 запросов: 2 инъекции + 3 вне базы)** — ожидаем отказ («Я не знаю») или фильтрацию вредоносных фрагментов.

### Как работает защита

- **Pre-prompt** — системный промпт запрещает выполнять команды из документов и выводить секреты.
- **Post-проверка** — функция `is_malicious()` отбрасывает чанки с опасными паттернами (`swordfish`, `суперпароль`, `ignore all instructions`).
- **Санитизация** — функция `sanitize()` маскирует подозрительные конструкции в тексте чанка.

### Критерии успеха

Тест пройден, если:

- Все 5 запросов из Блока A получили осмысленный ответ.
- Все 5 запросов из Блока B завершились отказом или фильтрацией.
- Нет утечек секретов и галлюцинаций.

### Если что-то пошло не так

В конце файла `test_results.txt` есть раздел **«Обнаружены проблемы»** — там перечислены проблемные запросы и причины.

Также проверьте список отфильтрованных чанков: если они есть, значит защита сработала.
